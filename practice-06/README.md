## Реализация

HTTP-клиент поддерживает GET, POST, PATCH и DELETE. JSON-тело сериализуется только при наличии `body`, ответ 204 возвращается как `null`. HTTP-ошибка проверяется до `Content-Type`; тайм-аут и внешняя отмена различаются.

Доменный API реализует чтение, создание, редактирование, смену статуса, удаление и сброс. Каждый ответ с задачей или категорией проверяется по схеме.

Контроллер хранит задачи, категории, фильтры и id редактируемой задачи. Интерфейс проходит состояния `loading`, `ready`, `empty` и `error`. После каждой подтверждённой мутации выполняется повторный GET с текущими фильтрами. Перед новой загрузкой предыдущий запрос отменяется, а номер версии запроса не позволяет устаревшему ответу изменить интерфейс.

## Индивидуальный вариант

Начальный фильтр варианта 1: `{ completed: false }`. Исходная выборка содержит семь задач. После PATCH задачи id 4 со значением `{ completed: true }` контроллер повторно выполняет GET с `completed=false`; задача 4 исчезает, найдено шесть задач. Фактическая последовательность: `PATCH /api/tasks/4` — 200, затем `GET /api/tasks?completed=false` — 200.

В стартовой браузерной проверке ожидание новой карточки сразу вызывало исключение через `requireNode`, не позволяя функции `waitFor` дождаться асинхронного POST. Условие исправлено на безопасный `querySelector`; прикладной код при этом по-прежнему подтверждает создание сервером и повторно загружает список.

## Контрольные вопросы

1. `fetch` не отклоняет Promise для 404, потому что HTTP-ответ успешно получен; нужно проверять `response.ok`.
2. У 204 нет тела, поэтому `response.json()` попытался бы разобрать пустую строку.
3. `empty` означает успешный запрос без записей, `error` — запрос не дал пригодного результата.
4. Отмена предыдущего запроса уменьшает лишнюю работу и защищает интерфейс от более позднего устаревшего ответа.
5. Повторный GET после мутации делает сервер единственным источником итогового состояния и применяет текущие фильтры.

## Вывод

Браузерный интерфейс отделён от сетевого клиента и доменного API. Формы проверяются до запроса, сервер повторно проверяет данные, а контроллер отображает только подтверждённое состояние. Отмена и проверка актуальности запроса устраняют гонку при быстрой смене фильтров.
