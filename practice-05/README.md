## Реализация

`api-client.js` формирует URL через `URL` и `URLSearchParams`, выполняет GET с `Accept: application/json`, проверяет HTTP-статус и `Content-Type`, разбирает JSON, поддерживает тайм-аут и внешний `AbortSignal`. Все ожидаемые отказы преобразуются в `ApiError` вида `http`, `network`, `invalid-response`, `timeout` или `aborted`.

`task-api.js` принимает только фильтры `completed`, `priority`, `categoryId` и `q`. До запроса проверяются параметры, после запроса — схема задач, категорий, уникальность id и соответствие `meta.total`. `loadInitialData` начинает запрос задач и категорий параллельно через `Promise.all`.

`fetchFn` передаётся клиенту явно, чтобы сетевое поведение проверялось без реального сервера. HTTP 404 не является сетевым отказом: `fetch` возвращает `Response`, поэтому `response.ok` проверяется отдельно.

## Контрольный сценарий

| Действие | Фактический результат | Итог |
|---|---|---|
| `GET /health` | 200, `{ status: "ok" }` | Пройдено |
| Получить все задачи | 12 задач, id `[1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34]` | Пройдено |
| `{ completed: false, priority: "high" }` | id `[4, 13, 34]`, `meta.total = 3` | Пройдено |
| Получить задачи и категории параллельно | Обе части результата доступны | Пройдено |
| `getTaskById(999)` | `kind = "http"`, `status = 404`, код `TASK_NOT_FOUND` | Пройдено |
| Повреждённый JSON / text | `invalid-response` | Пройдено |
| Задержка / явная отмена | `timeout` / `aborted` | Пройдено |

## Индивидуальный вариант

Вариант 1 использует `variantFilters = { completed: false }`. Запрос возвращает id `[4, 7, 13, 19, 22, 28, 34]`, `meta.total = 7`, что совпадает с таблицей вариантов.

## Вывод

Ожидание Promise описывает момент получения результата, но не означает успешный HTTP-статус. Клиент отдельно различает HTTP-ошибки, отсутствие соединения, неверный формат ответа, тайм-аут и отмену. Доменный модуль не передаёт интерфейсу данные, пока они не проверены по контракту.
